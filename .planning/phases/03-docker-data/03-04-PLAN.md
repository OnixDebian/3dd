<design_decisions>
PIN these:

- PROBE BEFORE TUI (ROB-01 / Pitfall 9): in main.rs, BEFORE `Tui::enter()` (braille) and
  BEFORE `run_kitty()` enters raw mode, call `docker::connect_and_probe().await`. On `Err(e)`:
  `eprintln!("{e}")` (the ProbeError Display carries the actionable message) and
  `std::process::exit(1)` — terminal is still cooked/normal, so the message is readable. On
  `Ok(docker)`: pass the handle into the chosen backend. The `--dump-rgba` path stays
  synthetic/offline (it's an inspection tool — keep it daemon-free; document that).
- CHANNEL OWNERSHIP: create the `mpsc::unbounded_channel::<DockerMsg>()` in main.rs (or in each
  backend entry), call `docker::spawn_docker_tasks(docker, tx)`, and hand `rx` to the backend.
- BRAILLE (App): add `docker_rx: UnboundedReceiver<DockerMsg>` and `live: LiveWorld` to App
  (App::new gains a constructor variant taking the rx, or a setter — keep App::new() default
  for tests/dump). In the main loop's existing drain pass (app.rs `run`), ADD a non-blocking
  drain: `while let Ok(msg) = self.docker_rx.try_recv() { if let Some(w) = self.live.apply(msg)
  { self.world = w; } }` once per loop iteration (same place Events are drained). The camera is
  framed to the scene at construction; when the live World's bounds change materially you MAY
  re-`frame_scene` (decision: re-frame on entity-count change only, to avoid per-sample camera
  jitter — document it). NO Docker calls inside `view()` or per frame. App still owns the World;
  ui::view is unchanged except the empty banner below.
- KITTY (run_kitty): it is currently a SYNC loop with its own `synthetic_scene()`. Make it
  live WITHOUT rewriting the renderer: keep run_kitty's structure but (a) accept the `rx` +
  Docker tasks, (b) since run_kitty is sync, drive the mpsc with a `tokio::runtime::Handle`
  (spawn the docker tasks on the runtime that main.rs is already on) and use
  `rx.try_recv()` (UnboundedReceiver::try_recv is non-blocking, no runtime needed to poll) each
  iteration to feed a `LiveWorld`, swapping the local `world` binding. Replace the
  `let world = synthetic_scene();` seed with `let mut live = LiveWorld::new();` + an initially
  empty World. `render_rgba(&world.entities, ...)` stays byte-for-byte. (If threading the rx
  into the sync loop proves awkward, the acceptable alternative is to convert run_kitty to an
  `async fn` run on the existing tokio runtime and `try_recv` in the loop — either way the
  render call and the 33ms pacing are unchanged. Document which path was taken.)
- EMPTY STATE (criterion #5, zero containers): when the live World has 0 entities, draw a
  centered plain-text banner instead of an empty scene:
    * braille: in ui::view, if `app.world.entities.is_empty()`, render a centered Paragraph
      ("No containers running — start one and it'll appear here") in the scene area instead of
      the Canvas. Keep the status bar.
    * kitty: if no entities, skip the rgba image and write a centered status line with the same
      message (you already write a status row; extend it / add a centered line).
  Never a blank void, never a panic on empty bounds.
- DAEMON DIES MID-SESSION (nice-to-have within criterion #5): if the events/stats tasks all end
  (sender dropped / stream errors), the last World stays on screen — do NOT crash. A full in-scene
  "daemon lost" banner is acceptable to defer to Phase 5 (ROB-02); the hard requirement here is
  no panic and no blank void. Document what was implemented.
- DO NOT modify render3d/ internals or kitty's render_rgba/emit_kitty — only the data source +
  the empty banner + the probe wiring. The whole point of Phase 3 is swapping the data source
  under an unchanged renderer.
- After wiring, run the app against the real daemon and CAPTURE evidence per the MEMORY note
  (screenshot-&-verify): run `--dump-rgba` is synthetic so instead, for kitty, briefly run the
  live app and confirm boxes match `docker ps`; for offline proof, you MAY add a tiny temporary
  one-shot that builds a LiveWorld from a single `list_containers` seed and dumps an rgba — but
  prefer a live visual check. Compare box COUNT to `docker ps -a` and colors to container states.
</design_decisions>
