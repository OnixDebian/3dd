<design_decisions>
PIN these:

- `cargo add bollard@0.21`. Confirm it resolves against the existing tokio 1.47 (STACK
  says bollard 0.21 needs tokio ^1.47 — already satisfied). Do not add other deps here.
- IMPORTANT: bollard 0.21 reorganized its generated types. Do NOT trust a remembered path.
  At execution time, confirm the exact paths via `cargo doc --open` or
  https://docs.rs/bollard/0.21.0 for: the `Docker` handle, `connect_with_local_defaults`,
  `version()`/`ping()`, the container-stats response type (likely
  `bollard::models::ContainerStatsResponse` / under `secret` or `models`), and
  `query_parameters::StatsOptions(Builder)`. Record the confirmed paths in the SUMMARY so
  03-03 doesn't re-discover them.
- Connection: `Docker::connect_with_local_defaults()` auto-discovers the unix socket /
  named pipe. Then PROBE with `version()` (or `ping()`).
- Failure classification (`ProbeError`): inspect the bollard error / underlying io error to
  distinguish:
    * SocketMissing  — the socket path does not exist (ENOENT). Message: "Docker socket not
      found at <path> — is Docker installed and running?"
    * PermissionDenied — EACCES connecting to the socket. Message: "Permission denied on
      <path> — add your user to the `docker` group or use the rootless socket."
    * DaemonDown — connection refused / daemon not responding. Message: "Docker daemon not
      reachable at <path> — is it running? (try: systemctl start docker)"
    * Other(String) — fallback with the underlying error text.
  Each variant carries an actionable plain-text string via `Display`. Best-effort
  classification is fine — when in doubt, DaemonDown with the raw error appended.
- `connect_and_probe()` returns `Result<Docker, ProbeError>`. It performs NO terminal I/O
  itself — the CALLER (main.rs, wired in 03-04) prints to stderr and exits BEFORE entering
  raw mode. Keep this function pure-ish (network probe only) so it stays testable/reusable
  by both backends.
- Domain model (domain.rs), bollard-FREE downstream:
    * `ContainerSnapshot { id: String, name: String, status: theme::Status, group_key: String }`
      — `id` is the real container id (string); `name` is the display name (strip leading
      '/'); `group_key` is the primary network name (or "" / "none" if none) — the future
      ENT-01 grouping axis and the layout group source. REUSE `theme::Status`; do NOT
      introduce a parallel status enum.
    * `fn map_status(state: &str, ...) -> theme::Status`: map Docker container state strings
      to Status: "running"->Running, "paused"->Paused, "restarting"->Restarting,
      "exited"/"dead"->Stopped, OOM/non-zero-exit or "dead"->Crashed (decision: treat
      `dead` and exited-with-nonzero as Crashed, plain exited(0) as Stopped — document the
      exact rule chosen). Unknown -> Stopped (safe default, visible-but-dim).
    * `fn from_bollard(...)`: map bollard's container summary/inspect + state into a
      `ContainerSnapshot`. This is the ONLY place bollard container types are touched.
  This is the boundary 03-03 fills with live data and 03-03/03-04 consume.
</design_decisions>
