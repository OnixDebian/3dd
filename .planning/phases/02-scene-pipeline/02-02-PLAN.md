Purpose: Deliver success criteria #1 (dozens of boxes read clearly), #2 (status color + load size), #3 (stable slots, via consuming 02-01's deterministic layout), and #4 (scene-framed orbit) on the braille backend.
Output: A multi-box braille render path wired into the app's scene canvas.

  <files>src/render3d/raster.rs, src/render3d/mod.rs</files>
  <action>
    Add `pub fn render_scene(entities: &[crate::world::entity::Entity], view: ViewParams, viewport: (usize, usize), palette: &Palette, config: &RenderConfig) -> Framebuffer` to `raster.rs`, and re-export it from `render3d/mod.rs`. Keep the existing single-cube `render()` (camera/tests still use it) — add, don't replace.

    Reuse the existing supersample buffer + AA-resolve + projector setup from `render()`. The change is the face-collection loop.

    CRITICAL DATA-MODEL CHANGE (the wiring the whole multi-box path hinges on — state it now, do NOT invent it at execution): today `RenderFace { indices: [usize;4], normal, distance }` stores INDICES into a single shared `cube.vertices` (raster.rs:189-194), and `fill_face(fb, projector, cube, &indices, color)` projects `cube.vertices[i]` (raster.rs:231-244). With many boxes there is NO single shared cube to index — each box has its OWN 8 world-transformed vertices, and the cross-box painter's sort must carry each face's own world vertices. So:
    - REDEFINE `RenderFace` to carry the face's 4 WORLD-SPACE vertices, NOT indices into a shared cube: `struct RenderFace { verts: [Vec3; 4], normal: Vec3, distance: f32, base: Color }`. Preferred approach: change the single `RenderFace` to hold `verts: [Vec3; 4]` and update the legacy `render()` to materialize its face's world verts (`cube.vertices[i]` for the 4 indices) when it builds each face — so BOTH paths share ONE face type and ONE `fill_face`. (Alternative if cleaner: keep the old indexed struct private to `render()` and add a separate `SceneFace { verts, normal, distance, base }` for the scene path. Either way, the scene faces MUST carry world verts.)
    - CHANGE `fill_face`'s signature to take the world verts directly instead of `(cube, &indices)`: `fn fill_face(fb: &mut Framebuffer, projector: &Projector, verts: &[Vec3; 4], color: Color)`. Its body projects `verts[k]` (not `cube.vertices[indices[k]]`); everything downstream (the two `fill_triangle` calls) is unchanged. Update `render()`'s single `fill_face` call site to pass its face's 4 world verts. This signature change is load-bearing — it is what lets per-box world vertices reach the fill.

    The face-collection loop for `render_scene`:
    1. Build ONE `Vec<RenderFace>` spanning EVERY box. For each entity, transform the unit cube's 8 vertices into WORLD space (translate by `entity.position`, scale by `entity.half_extents * 2` since the unit cube spans +/-0.5 -> a box of side `2*half_extent`); store these 8 world verts in a local `[Vec3; 8]`. For each of the cube's 6 faces, gather the face's 4 WORLD verts (`world_verts[face.indices[k]]`) into the new `RenderFace.verts`. Compute the face's WORLD-space centroid (mean of its 4 world verts) and outward normal (rotation-free here — axis-aligned boxes — so the unit-cube face normal IS the world normal). Back-face cull per face as today (`normal.dot(view.eye - centroid) > 0`), and store `distance = (view.eye - centroid).length()`.
    2. Carry each face's per-box base color: `palette.status_color(entity.status)` (CONT-01). Store it on the RenderFace `base` field so the fill uses the right status color per box.
    3. CROSS-BOX PAINTER'S SORT (the critical correctness step): sort the SINGLE combined face list farthest-first by `RenderFace.distance` (world-space camera distance to the face centroid). This is what makes a near box occlude a far box — do NOT sort per-box then concatenate. (No per-pixel z-buffer; painter's sort over convex axis-aligned boxes is sufficient per PITFALLS #4. Note any residual cyclic-overlap risk in the SUMMARY for the human-verify in 02-04.)
    4. Fog: compute the distance range across ALL visible faces (scene-wide near/far) so far boxes dim and near boxes stay bright — depth reads at scale. Apply the existing orientation-Lambert + fog shading per face, using that face's `base` color.
    5. Fill each face with the new `fill_face(&mut hi, &projector, &rf.verts, color)` into the supersampled buffer; resolve with the existing `resolve_supersampled` (dominant-color-per-dot, flat faces — keep it).

    Each entity's 8 world verts are computed ONCE per box (step 1) and the 6 faces reference them, so shared corners aren't recomputed. `fill_face` re-projects 4 corners per face (acceptable at this scale; if you want to avoid re-projecting shared corners, project the 8 world verts once per box and pass projected 2D points — optional). Skip a face if any corner clips (existing behavior); the scene-framing camera (Task 2) keeps boxes in-frustum so this should be rare.

    Tests (headless, no terminal):
    - `render_scene` with a small hand-built 2-entity scene where box A is clearly in front of box B along the view axis: assert the center overlap region resolves to box A's status color, NOT box B's (inter-box occlusion proof).
    - AT-SCALE ORDERING (automated guard for success criteria #1 "no noise collapse at scale" and #3 "stable" — so cross-box ordering isn't solely human-judged in 02-04): build a small DETERMINISTIC multi-box grid scene (e.g. a hand-built ~9-box grid, or 3x3) with a KNOWN near box and a KNOWN far box that overlap at a SPECIFIC viewport pixel along the view axis. Assert that exact pixel resolves to the NEAR box's status color, NOT the far box's — proving the SINGLE combined cross-box sort orders correctly when many faces from many boxes compete, not just in the trivial 2-box case.
    - `render_scene` with entities of different statuses yields >= 2 distinct colors in the framebuffer (per-box status color is applied).
    - empty scene (`&[]`) returns an all-unlit framebuffer without panicking.
    - a box far from center still lands inside the framebuffer when framed by a scene-radius view (sanity; can build the view from a literal eye/target).
  </action>
